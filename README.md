# Battleship (Unity)

Морской бой на двоих с авторитарным сервером. Сервер и два клиента живут в одном процессе Unity и общаются через эмулируемый сетевой канал (задержка, потери пакетов, разрыв и переподключение).

## Как запустить

1. Unity **6000.5.1f1**
2. Открыть корень репозитория как Unity-проект.
3. Открыть сцену `Assets/Scenes/SampleScene.unity` и нажать **Play**. Всё остальное (сеть, сервер, клиенты, UI) создаётся кодом при старте: `BattleBootstrap` вешается на `RuntimeInitializeOnLoadMethod`, а `BattleSceneSetup` собирает сцену.

Управление:

- клик по клетке **вражеского** поля стреляет (только когда твой ход);
- **Disconnect / Reconnect** у каждого игрока рвут и восстанавливают его канал вручную;
- **Restart** пересоздаёт сессию;
- если игрока отключило не кнопкой (например, канал умер из-за потерь), UI сам переподключает его через 1.5 с (`BattleGameUI.reconnectDelay`).

Параметры:

- правила игры: `Assets/Resources/BattleshipConfig.asset` (размер поля, длины кораблей, `reconnectGraceSeconds`);
- эмуляция сети: `latencyMs` (по умолчанию 120), `packetLoss` (по умолчанию 0), `retryTimeout`, `maxRetries` в компоненте `BattleSceneSetup`. Значения копируются в транспорт один раз при старте, поэтому менять их нужно до Play: либо в коде, либо добавив `BattleSceneSetup` на объект сцены вручную (тогда бутстрап возьмёт существующий).

## Архитектура

```
BattleClient <-> ReliableOrderedTransport <-> LocalTransport <-> ReliableOrderedTransport <-> BattleServer

```

1. Сервер авторитарен: только он знает расстановку и решает, попадание это или нет. Клиент шлёт fire в (x, y) и получает результат.
2. `BattleServer` держит два `BattlePlayer`, у каждого своя `BattleBoard` (корабли, выстрелы). Расстановка случайная, реализована в  `BattleShipPlacer`.
3. `BattleClient` (разбит на partial-файлы: Core / Messages / Outgoing / Snapshot / Board) хранит только то, что игроку нужно знать: свои корабли и результаты выстрелов по врагу.
4. UI (`BattleGameUI`, `BattleFieldView`) ничего не знает про сеть: следит за счётчиком `BattleClient.StateVersion` и перерисовывается, когда он изменился.
5. Транспорт спрятан за `INetworkTransport`. Сервер и клиент от конкретной реализации не зависят.
6. `LocalTransport` эмулирует канал: задержка через корутину, случайная потеря пакетов, разрыв.
7. `ReliableOrderedTransport` — декоратор поверх любого транспорта, минимальная реализация надежного транспорта: нумерует пакеты, подтверждает (ACK), повторяет неподтверждённые каждые `retryTimeout` секунд и отдаёт получателю строго по порядку, отбрасывая дубли.
8. Если пакет не удалось доставить за `maxRetries` попыток, надёжный слой сам объявляет разрыв.
9. Формат сообщения: 1 байт `MessageType` + JSON (`JsonUtility`) со структурой сообщения.

## Сообщения

Клиент → сервер:

| Сообщение | Поля | Зачем |
|---|---|---|
| `Fire` | `X, Y` | выстрел |
| `Ping` | `Id` | замер RTT |
| `ReconnectRequest` | `PlayerId` | оповещение сервера о переподключении |

Сервер → клиент:

| Сообщение | Поля | Зачем |
|---|---|---|
| `GameStarted` | `PlayerId, BoardWidth, BoardHeight` | начало партии, твой id и какое поле |
| `ShipPlacement` | размеры, координаты, ориентации | расстановка только своих кораблей |
| `TurnChanged` | `PlayerId` | чей ход |
| `FireResult` | `X, Y, Hit, Sunk, AlreadyShot, Rejected` | ответ стрелявшему |
| `OpponentFire` | `X, Y, Hit, Sunk` | сообщение обороняющемуся, что по нему стреляли |
| `GameOver` | `WinnerPlayerId` | конец партии |
| `PauseChanged` | `Paused` | пауза, если соперник отвалился, и снятие паузы |
| `Notice` | `Text` | текст для игрока (Not your turn, Opponent disconnecte) |
| `GameStateSnapshot` | всё состояние партии с точки зрения игрока | ответ на `ReconnectRequest` |
| `Pong` | `Id` | ответ на `Ping` |

Поверх этого `ReliableOrderedTransport` добавляет свой заголовок: тип пакета (`Data` / `Ack`) и номер последовательности.

## Что происходит при разрыве

1. **Обнаружение.** Разрыв виден по-разному: явный `Disconnect()` (кнопка) или надёжный слой исчерпал `maxRetries` (при `retryTimeout = 0.5 с` это около 5 секунд без единого ACK). В обоих случаях сервер получает событие `Disconnected` для этого игрока.
2. **Пауза.** Сервер запускает для игрока таймер `DisconnectedFor`, шлёт оставшемуся сопернику `Notice` и `PauseChanged(true)`. Пока кто-то из игроков не в сети, выстрелы отклоняются (`FireResult.Rejected` + `Notice`), ход не переходит.
3. **Переподключение.** Канал восстанавливается (кнопка или автоматически через 1.5 с). Оба конца транспорта сбрасывают счётчики последовательности и очищают очереди. Клиент шлёт `ReconnectRequest{PlayerId}`.
4. **Восстановление.** Сервер отвечает `GameStateSnapshot`: размер поля, чей ход, свои корабли с подбитыми клетками, все выстрелы в обе стороны, результаты своих выстрелов. Клиент полностью перезаписывает состояние, сбрасывая незавершённые выстрелы, потому что ответ на них мог потеряться. Сопернику уходит `PauseChanged(IsPaused)` и уведомление.
5. **Таймаут.** Если игрок не вернулся за `reconnectGraceSeconds` (20 с по умолчанию), победа присуждается сопернику: `GameOver` + `Notice`. Значение `0` отключает таймаут, тогда сервер ждёт бесконечно.
6. Разрыв после конца партии игнорируется.

## Принятые решения и упрощения

- Пауза при разрыве вместо мгновенного поражения, с окном на возвращение (`reconnectGraceSeconds`), потом техническая победа соперника.
- Состояние при возврате восстанавливается снапшотом

Что упрощено:

- Сети нет: транспорт внутрипроцессный (`LocalTransport`). Интерфейс `INetworkTransport` позволяет подставить сокеты, но такой реализации нет.
- **UI собирается кодом** (`BattleSceneSetup`), а не префабами и сценой: проект запускается настройки, но редактировать такой UI неудобно.
- Нет автотестов. Логика сервера (`BattleBoard`, `BattleShipPlacer`, `BattleServer`) не зависит от MonoBehaviour в основном коде и хорошо ложится на тесты, но написаны они не были. Поведение проверялось вручную в Play Mode
- Логи идут только в консоль, отдельно прочитать их в игре нельзя
